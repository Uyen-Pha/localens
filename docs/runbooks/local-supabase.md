# Local Supabase Task16 runbook

## Current status

The local container prerequisite is available on the Windows host. Docker
Desktop was installed per-user with the WSL2 Linux-container backend; Windows
containers were not enabled. Host verification on 2026-09-01 recorded:

- WSL app `2.7.12.0`, kernel `6.18.33.2-2`, Windows `10.0.26200.9168`.
- Docker Desktop `4.88.1.237512` and Docker client/server `29.7.2`.
- Engine `OS=linux`, `ARCH=amd64`, `OSTYPE=linux`, and storage driver
  `overlayfs`.
- `docker run --rm hello-world` exited `0` and printed
  `Hello from Docker!`.

Verify the host engine, not only the installed executable:

```powershell
wsl.exe --status
docker version
docker info
docker run --rm hello-world
```

Both client and server sections must be present, `docker info` must report a
Linux engine, and the test container must exit `0`. The per-user engine is
session-dependent: after a Windows restart or sign-out, start Docker Desktop
again and wait for the engine before rerunning these checks. If an installer
reports that a restart is required, stop and restart manually; this runbook
must never trigger a restart automatically.

These results establish host runtime readiness only. A restricted Codex
sandbox can still receive access-denied errors for
`%USERPROFILE%\.docker\config.json` or `npipe:////./pipe/docker_engine`; those
errors describe sandbox access to the per-user configuration or named pipe,
not a failed host engine. Run engine verification in an approved host context
when the sandbox cannot access them.

The repository still does not install a Supabase CLI implicitly, connect to a
remote project, or generate `database.types.ts` without a successful local
schema command. Until the reviewed project-local CLI is installed,
`pnpm db:types:check` truthfully stops with `SUPABASE_CLI_NOT_FOUND`; that is a
separate project-tooling gate, not a container-runtime failure.

Required local prerequisites:

- Docker Desktop with a working WSL2 Linux-container engine, verified with the
  four host commands above.
- Node 24 and pnpm 11, matching `package.json`.
- The reviewed, exact project-local `supabase@2.115.0` dev dependency. Add it
  only after Docker is available and only through the normal dependency review.

Do not run `supabase link`, use `--project-ref`, use `--db-url`, or run any
remote reset/push/pull command for this milestone. The wrapper rejects those
modes.

## Gate order

After the prerequisites are intentionally installed, run from the repository
root:

```powershell
pnpm install --frozen-lockfile
pnpm db:static:seed
```

After the approval gate is satisfied, bootstrap the generated type file once
against the freshly reset local schema:

```powershell
pnpm db:start
pnpm db:reset
pnpm db:types
pnpm db:stop
```

Then run the verification gate and the remaining checks:

```powershell
pnpm db:verify
pnpm peers check
pnpm lint
pnpm typecheck
pnpm test:run
pnpm build
```

On the current branch, `pnpm db:static:seed` is expected to stop at the
draft-approval gate until the catalog is reviewed and approved. Do not treat
that expected stop as a runtime failure, and do not proceed to claim the
database gate passed.

`pnpm db:verify` runs the local-only steps in this order and always attempts
cleanup:

```text
db:start -> db:reset -> db:lint -> db:test -> db:concurrency -> db:types:check -> db:stop
```

The first failed step remains the primary failure. A cleanup failure is
reported separately. `db:reset` is destructive to the local container only;
never substitute a linked or remote database.

The generated-types scripts run
`supabase gen types --lang typescript --local` through the project-local CLI.
Writes use a temporary sibling file followed by an atomic rename. Drift checks
compare the generated bytes with the existing file and never create a missing
target. Empty or failed CLI output is an error.

## Local runtime Auth identities

The runtime Auth seed creates exactly these local test-only accounts:

- `customer.runtime@localens.test` with the authoritative `customer` database role.
- `guide.runtime@localens.test` with the authoritative `guide` database role and a guide profile.
- `admin.runtime@localens.test` with the authoritative `admin` database role.

Supply each password only through its named environment variable. Do not put
password values in this runbook, tracked environment files, shell history, or
command output. From the repository root, use the local Supabase database URL
and inject temporary local-only passwords into the current process before
running:

```powershell
$env:LOCALENS_DB_URL = 'postgresql://postgres:postgres@127.0.0.1:54322/postgres'
$env:LOCALENS_RUNTIME_CUSTOMER_PASSWORD = '<temporary local-only customer password>'
$env:LOCALENS_RUNTIME_GUIDE_PASSWORD = '<temporary local-only guide password>'
$env:LOCALENS_RUNTIME_ADMIN_PASSWORD = '<temporary local-only admin password>'
try {
  pnpm db:reset
  pnpm db:seed:runtime-auth
  pnpm db:seed:runtime-auth
  pnpm db:test
} finally {
  Remove-Item Env:LOCALENS_RUNTIME_CUSTOMER_PASSWORD -ErrorAction SilentlyContinue
  Remove-Item Env:LOCALENS_RUNTIME_GUIDE_PASSWORD -ErrorAction SilentlyContinue
  Remove-Item Env:LOCALENS_RUNTIME_ADMIN_PASSWORD -ErrorAction SilentlyContinue
}
```

The second seed run is intentional and must reuse the same three Auth users.
The script obtains only the API URL and service-role key from captured local
CLI status, never prints that captured status, and refuses to proceed unless
both Supabase and PostgreSQL endpoints are loopback on the standard local
ports. It normalizes only `private.user_roles`, `public.profiles`, and
`public.guide_profiles`. It does not seed or modify catalog, food, tour,
departure, booking, payment, or other inventory/transaction data.

## Two-session concurrency gate

The harness uses two independent PostgreSQL clients and runs only against the
loopback Supabase database. Start and reset Supabase, then configure the local
URL explicitly before running it in PowerShell:

```powershell
$env:LOCALENS_DB_URL = 'postgresql://postgres:postgres@127.0.0.1:54322/postgres'
$env:LOCALENS_DB_CONCURRENCY = '1'
pnpm db:concurrency
```

Use the same two environment variables when running `pnpm db:verify`. Without
them, the gate fails closed with `NOT_CONFIGURED`; without the project-local
CLI or local database, it returns `NOT_AVAILABLE`. A successful run executes:

1. CAS revision winner.
2. Guest claim winner.
3. Quota bucket creation and reservation idempotency.
4. Departure capacity without oversell.
5. Quote checkout compensation.
6. Stripe webhook event race.

If `LOCALENS_DB_URL` is provided, it must be a loopback-only PostgreSQL URL
(`localhost`, `127.0.0.1`, or `[::1]`) using the default local Supabase port
`54322`. Remote hosts and non-local ports are rejected as
`REMOTE_MODE_REJECTED`.

Only a container-backed pgTAP run plus the real two-session harness can support
claims about PostgreSQL syntax, RLS behavior, transaction locks, state guards,
or concurrency. Static SQL/artifact tests remain useful but do not replace
this gate.
